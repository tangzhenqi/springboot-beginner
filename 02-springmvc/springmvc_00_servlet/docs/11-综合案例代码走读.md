# 11 综合案例代码走读

对应代码：`BaseServlet`、`UserServlet`、`UserService`、`UserDao`、`User`、`LoginCheckFilter`

这一篇把前面的知识点串起来，完整讲清楚「用户登录 + 增删改查」是怎么跑起来的。

## 一、整体架构

```
                        浏览器
                          │
    ┌─────────────────────┼─────────────────────┐
    │  CharacterEncodingFilter  (/*)  统一编码   │
    │             ↓                             │
    │  LoginCheckFilter  (/user/*)  登录校验     │   Web层组件
    │             ↓                             │
    │  UserServlet extends BaseServlet          │
    │      反射分发 → list()/save()/delete()...  │
    └─────────────────────┼─────────────────────┘
                          ↓
                    UserService              业务层：业务逻辑、校验
                          ↓
                     UserDao                 数据层：数据存取
                          ↓
              ConcurrentHashMap（模拟数据库）
                          
                  ↓ 返回视图名 ↓
              WEB-INF/pages/*.jsp            视图层：EL + JSTL 渲染
```

### 为什么要分三层

| 层 | 职责 | 本案例的类 | 不该做的事 |
| --- | --- | --- | --- |
| **表现层** | 接收参数、调用业务、返回视图 | `UserServlet` | 不该写业务规则、不该直接操作数据 |
| **业务层** | 业务逻辑、校验、事务 | `UserService` | 不该出现 request/response |
| **数据层** | 数据的增删改查 | `UserDao` | 不该有业务判断 |

**判断分层是否合理的标准**：如果把表现层从 Servlet 换成命令行程序、或换成 SpringMVC，
业务层和数据层的代码应该**一行都不用改**。

本案例的 `UserService` 里没有任何 `HttpServletRequest`，就是这个原则的体现：

```java
// ✅ 业务层只接收业务参数
public User login(String username, String password) { ... }

// ❌ 反面写法：业务层依赖了Web层的对象，换个表现层就废了
public User login(HttpServletRequest request) { ... }
```

## 二、BaseServlet：手写简易版 DispatcherServlet（核心）

### 1. 解决什么问题

按最朴素的写法，用户模块需要这么多 Servlet：

```
LoginServlet       → /user/login
LogoutServlet      → /user/logout
UserListServlet    → /user/list
UserSaveServlet    → /user/save
UserUpdateServlet  → /user/update
UserDeleteServlet  → /user/delete
```

**6 个类，每个类都要写 doGet/doPost、都要重复处理跳转逻辑。** 模块一多就是几百个类。

### 2. 思路

一个 Servlet 用**目录匹配** `/user/*` 接管整个模块，
再根据**路径的最后一段**决定调用哪个方法：

```
/user/list    →  截取出 "list"    →  反射调用 list(request, response)
/user/save    →  截取出 "save"    →  反射调用 save(request, response)
/user/delete  →  截取出 "delete"  →  反射调用 delete(request, response)
```

### 3. 完整实现

```java
public abstract class BaseServlet extends HttpServlet {

    private static final String REDIRECT_PREFIX = "redirect:";

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        // ① 从请求路径中截取方法名：/user/list → list
        String uri = request.getRequestURI();
        String methodName = uri.substring(uri.lastIndexOf('/') + 1);
        if (methodName.isEmpty()) {
            response.sendError(HttpServletResponse.SC_NOT_FOUND, "请求路径不完整：" + uri);
            return;
        }

        try {
            // ② 找到子类中的同名方法
            Method method = getClass().getDeclaredMethod(methodName,
                    HttpServletRequest.class, HttpServletResponse.class);

            // ③ 反射调用
            Object result = method.invoke(this, request, response);

            // ④ 根据返回值决定跳转方式
            if (result instanceof String) {
                String view = (String) result;
                if (view.startsWith(REDIRECT_PREFIX)) {
                    response.sendRedirect(request.getContextPath()
                            + view.substring(REDIRECT_PREFIX.length()));
                } else {
                    request.getRequestDispatcher(view).forward(request, response);
                }
            }
            // result为null表示方法内部已经响应过了（如写json），不做处理

        } catch (NoSuchMethodException e) {
            response.sendError(HttpServletResponse.SC_NOT_FOUND,
                    "找不到处理方法：" + getClass().getSimpleName() + "#" + methodName + "()");
        } catch (IllegalAccessException | InvocationTargetException e) {
            throw new ServletException("请求处理失败：" + methodName,
                    e.getCause() == null ? e : e.getCause());
        }
    }
}
```

### 4. 四个设计细节

**① 为什么重写 `service()` 而不是 `doGet/doPost`？**

因为要接管**所有请求方式**。如果重写 `doGet`，POST 请求就走不到这里。
`HttpServlet.service()` 是分发的源头，重写它就绕过了按请求方式分发的逻辑。

**② 为什么用 `getClass()` 而不是 `BaseServlet.class`？**

```java
Method method = getClass().getDeclaredMethod(methodName, ...);
```

`getClass()` 返回的是**运行时的真实类型**，也就是 `UserServlet`。
用 `BaseServlet.class` 只能找到基类自己的方法，子类的方法一个都找不到。

这也是为什么 `BaseServlet` 声明为 `abstract` —— 它不该被直接使用，只作为基类存在。

**③ 返回值约定的设计**

| 返回值 | 行为 |
| --- | --- |
| `"/WEB-INF/pages/list.jsp"` | 转发到该页面 |
| `"redirect:/user/list"` | 重定向（自动补虚拟目录） |
| `null` | 什么都不做（方法内部已响应，如写 json） |

**故意和 SpringMVC 保持一致**，学完这个再看 SpringMVC 的 `return "redirect:/user/list"`
会觉得非常自然。

**④ 异常处理**

反射调用时，业务方法抛出的异常会被包装成 `InvocationTargetException`，
真正的异常在 `getCause()` 里。所以要拆包，否则日志里全是无用的反射堆栈：

```java
throw new ServletException("请求处理失败：" + methodName, e.getCause() == null ? e : e.getCause());
```

而 `NoSuchMethodException` 意味着「路径不存在」，语义上是 **404 而不是 500**，所以单独捕获。

### 5. 局限性（正是 SpringMVC 要解决的）

| 局限 | SpringMVC 的解法 |
| --- | --- |
| 方法名必须等于 url 最后一段，改路径就要改方法名 | `@RequestMapping("/xxx")` 解耦路径和方法名 |
| 参数只能是 `(request, response)` 两个固定形参 | 参数解析器：想写什么参数就写什么参数 |
| 参数要手动 `getParameter` + 类型转换 | 自动封装实体、自动类型转换 |
| 无法区分 GET/POST | `@GetMapping`/`@PostMapping` |
| 返回 json 要手动拼 | `@ResponseBody` |
| 每次请求都反射查找方法，无缓存 | `HandlerMapping` 启动时建立映射表并缓存 |
| 视图路径写死在方法里 | `ViewResolver` 配置前缀后缀 |

## 三、请求的完整生命周期

以「登录后查看用户列表」为例，走一遍全流程：

```
1. 浏览器发起：GET http://localhost/user/list
                    │
2. Tomcat 接收，解析报文，创建 request/response 对象
                    │
3. 匹配过滤器链
   ├─ CharacterEncodingFilter (/*)  匹配 ✅
   │    request.setCharacterEncoding("UTF-8")
   │    chain.doFilter() 放行
   │
   └─ LoginCheckFilter (/user/*)  匹配 ✅
        path = "/user/list"，不在白名单
        session.getAttribute("loginUser") != null  → 已登录
        chain.doFilter() 放行
                    │
4. 匹配 Servlet：UserServlet (/user/*)  目录匹配 ✅
   Tomcat 调用 service(request, response)
                    │
5. BaseServlet.service()
   uri = "/user/list"  →  methodName = "list"
   反射找到 UserServlet.list(HttpServletRequest, HttpServletResponse)
   method.invoke(this, request, response)
                    │
6. UserServlet.list()
   userService.findAll()  →  UserDao.findAll()  →  返回 List<User>
   request.setAttribute("userList", userList)
   return "/WEB-INF/pages/list.jsp"
                    │
7. BaseServlet 拿到返回值
   不以 "redirect:" 开头 → 转发
   request.getRequestDispatcher("/WEB-INF/pages/list.jsp").forward(...)
                    │
8. list.jsp 被翻译成 Servlet 执行
   ${sessionScope.loginUser.username}  从 session 域取
   <c:forEach items="${userList}">     从 request 域取
   渲染出完整 HTML
                    │
9. 响应返回，过滤器的"放行后"代码执行（本案例为空）
                    │
10. 浏览器渲染页面，request 对象销毁
```

**建议对着这个流程在代码里打断点走一遍，比看十遍文档都管用。**

## 四、九个功能逐个拆解

### 1. `toLogin` —— 跳转登录页 + Cookie 回显

```java
public String toLogin(HttpServletRequest request, HttpServletResponse response) {
    Cookie[] cookies = request.getCookies();
    if (cookies != null) {                       // ⚠️ 无cookie时返回null
        for (Cookie cookie : cookies) {
            if ("rememberedUsername".equals(cookie.getName())) {
                request.setAttribute("rememberedUsername", decode(cookie.getValue()));
                break;
            }
        }
    }
    return "/WEB-INF/pages/login.jsp";
}
```

知识点：Cookie 遍历、url 解码、request 域、转发。

### 2. `login` —— 登录

```java
public String login(HttpServletRequest request, HttpServletResponse response) {
    User user = userService.login(request.getParameter("username"),
                                  request.getParameter("password"));
    if (user == null) {
        request.setAttribute("errorMsg", "用户名或密码错误");
        request.setAttribute("username", username);     // 回显
        return "/WEB-INF/pages/login.jsp";              // 转发，保住errorMsg
    }
    request.getSession().setAttribute(SESSION_USER, user);   // 存Session
    // ... 写Cookie ...
    return "redirect:/user/list";                            // 重定向，防重复提交
}
```

知识点：参数获取、Session、Cookie、**失败转发 vs 成功重定向**。

注意业务层的这个细节：

```java
// UserService.login()
if (user == null || !user.getPassword().equals(password)) {
    return null;    // 用户不存在和密码错误返回同样的结果
}
```

**对外不区分「用户不存在」和「密码错误」**，否则攻击者可以用它枚举出系统里有哪些用户名。

### 3. `logout` —— 退出

```java
HttpSession session = request.getSession(false);   // 不存在就不创建
if (session != null) {
    session.invalidate();                          // 整个销毁
}
return "redirect:/user/toLogin";
```

### 4. `list` —— 列表

```java
List<User> userList = userService.findAll();
request.setAttribute("userList", userList);
return "/WEB-INF/pages/list.jsp";
```

最标准的「查数据 → 存域 → 转发」三段式。

### 5. `toAdd` / `save` —— 新增

```java
public String save(HttpServletRequest request, HttpServletResponse response) {
    User user = buildUserFromRequest(request);        // 手动封装

    if (user.getUsername() == null || user.getUsername().trim().isEmpty()) {
        request.setAttribute("errorMsg", "用户名不能为空");
        return "/WEB-INF/pages/add.jsp";
    }
    if (!userService.save(user)) {                    // 业务层判断重名
        request.setAttribute("errorMsg", "用户名 " + user.getUsername() + " 已存在");
        request.setAttribute("user", user);           // 把填过的数据带回去
        return "/WEB-INF/pages/add.jsp";
    }
    return "redirect:/user/list";
}
```

**两层校验的分工**：

- 表现层：**格式校验**（非空、长度、格式），因为它属于「输入合法性」
- 业务层：**业务校验**（用户名唯一、余额是否充足），因为它需要查数据、属于业务规则

### 6. `toUpdate` / `update` —— 修改

修改的关键是**回显**和**主键传递**：

```java
public String toUpdate(HttpServletRequest request, HttpServletResponse response) {
    Integer id = parseInt(request.getParameter("id"));
    User user = id == null ? null : userService.findById(id);
    if (user == null) {
        request.setAttribute("errorMsg", "要修改的用户不存在");
        return list(request, response);       // ★ 直接复用list方法
    }
    request.setAttribute("user", user);
    return "/WEB-INF/pages/update.jsp";
}
```

`return list(request, response)` 这个写法值得注意：**直接调用另一个处理方法**，
它会把 `userList` 也存进域，然后返回列表页的路径。
错误提示和列表数据同时具备，一次转发搞定 —— 这也是转发（而非重定向）才能做到的。

页面上用隐藏域传主键：

```jsp
<input type="hidden" name="id" value="${user.id}">
```

**为什么不放在 url 上？** 因为表单是 POST 提交的，url 上的参数容易被用户改；
更重要的是，隐藏域会随表单一起提交，和其他字段统一处理。

### 7. `delete` —— 删除

```java
public String delete(HttpServletRequest request, HttpServletResponse response) {
    Integer id = parseInt(request.getParameter("id"));
    if (id == null || !userService.deleteById(id)) {
        request.setAttribute("errorMsg", "删除失败，用户不存在");
        return list(request, response);
    }
    return "redirect:/user/list";
}
```

页面上加了二次确认：

```jsp
<a href="${pageContext.request.contextPath}/user/delete?id=${user.id}"
   onclick="return confirm('确定要删除【${user.username}】吗？')">删除</a>
```

`onclick` 返回 false 会阻止 `<a>` 的默认跳转。

> ⚠️ **删除用 GET 请求是不规范的**（GET 应该是幂等的、无副作用的），
> 容易被爬虫和浏览器预加载误触发。规范做法是用 POST 或 DELETE，
> 这在 `springmvc_06_rest` 模块里会讲。这里为了简化演示保留了 GET。

### 8. `listJson` —— JSON 接口

```java
public String listJson(HttpServletRequest request, HttpServletResponse response) throws IOException {
    response.setContentType("application/json;charset=UTF-8");
    // ... 手动拼接json ...
    response.getWriter().write(json.toString());
    return null;     // ★ 告诉BaseServlet：我自己响应了，别跳页面
}
```

**返回 `null` 这个约定**在这里体现了价值：同一套分发机制，既能返回页面，也能返回数据。

## 五、数据层：为什么用内存 Map

```java
public class UserDao {
    private static final ConcurrentHashMap<Integer, User> DB = new ConcurrentHashMap<>();
    private static final AtomicInteger ID_GENERATOR = new AtomicInteger(0);

    static {
        save(new User(null, "admin", "123456", "男", 20, "北京市海淀区"));
        save(new User(null, "tom", "123456", "男", 25, "上海市浦东新区"));
    }
}
```

**理由：本模块要讲的是 Servlet，不该被数据库环境搭建、JDBC、连接池这些事分散注意力。**

三个设计点：

1. **`ConcurrentHashMap` 而不是 `HashMap`** —— Servlet 是多线程的，
   多个请求同时增删会导致 `HashMap` 数据错乱甚至死循环
2. **`AtomicInteger` 模拟主键自增** —— 同理，`id++` 会有并发问题
3. **`static` + 静态代码块** —— 数据随类加载初始化一次，所有请求共享，
   相当于一个"活在内存里的数据库"

⚠️ **数据存在内存，重启服务就恢复初始状态**，这是预期行为。

在 `springmvc_08_ssm` 模块里，这一层会被 MyBatis 的 Mapper 接口替换掉，
而 `UserService` 和上层代码几乎不用改 —— **这就是分层的好处**。

## 六、这个案例还缺什么（生产级差距）

作为教学案例它是完整的，但离生产还有距离，知道差在哪同样重要：

| 缺失项 | 后果 | 正确做法 |
| --- | --- | --- |
| 密码明文存储 | 数据泄露即全军覆没 | BCrypt / Argon2 加盐哈希 |
| 无 CSRF 防护 | 恶意站点可诱导用户执行删除 | CSRF Token |
| 删除用 GET | 可被预加载误触发 | POST / DELETE |
| 无分页 | 数据量大时页面卡死 | limit / offset 分页 |
| 无事务 | 多步操作可能只成功一半 | `@Transactional` |
| 前端无校验 | 无效请求打到服务器 | 前端校验 + 后端校验双保险 |
| 异常信息直接展示 | 泄露内部结构 | 统一异常处理 + 脱敏日志 |
| 无操作日志 | 出问题无法追溯 | AOP 记录操作日志 |

这些在后续的 SpringMVC / SpringBoot 模块里会逐步补齐。

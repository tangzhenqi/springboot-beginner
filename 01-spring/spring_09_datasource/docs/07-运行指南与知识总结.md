## 13. 构建与运行

### 13.1 构建

在案例目录中执行：

```bash
mvn clean package
```

本案例已验证可以通过 Maven 编译打包。

### 13.2 在 IDE 中运行

最直接的方式是用 IDE 运行：

```text
com.spring.App.main()
```

如果 MySQL 可访问，会看到：

1. Druid 状态信息；
2. C3P0 初始化日志和池配置；
3. `book dao save ...root666`。

由于 C3P0 会尝试预建连接，MySQL 不可用时可能出现重试日志或连接异常。旧版 MySQL 驱动还可能输出 SSL 相关警告，这与业务 `save()` 的打印不是一回事。

## 14. 一句话理解每个核心配置

```xml
<bean id="..." class="...">
```

让 Spring 创建并管理一个对象。

```xml
<property name="x" value="y"/>
```

调用 `setX(y)` 注入一个简单值。

```xml
<context:property-placeholder location="..."/>
```

加载外部 properties，让 XML 可以使用占位符。

```xml
value="${jdbc.url}"
```

用 properties 中 `jdbc.url` 对应的值替换当前位置。

```java
ctx.getBean("beanId")
```

从 Spring 容器取出已经创建、配置完成的对象。

## 15. 知识点总结

1. Spring IoC 不只能管理自定义类，也能管理 Druid、C3P0 等第三方类。
2. XML 的 `<property>` 本质上是基于 JavaBean setter 进行属性注入。
3. 同一个业务含义在不同第三方类中可能使用不同属性名，必须以类实际提供的 setter 为准。
4. `DataSource` 是标准抽象，应用代码应优先面向它编程，而不是绑定具体连接池类型。
5. `<context:property-placeholder>` 能把易变配置从 XML 抽取到 `.properties` 文件。
6. `${jdbc.username}` 与 `${username}` 是两个完全不同的键；前者来自 `jdbc.properties`，后者来自 `jdbc2.properties`。
7. `system-properties-mode="NEVER"` 可阻止 JVM 系统属性参与占位符解析，但使用明确的属性前缀仍然很重要。
8. 创建数据源对象不等于已经建立数据库连接；真正的连接时机取决于连接池实现和初始化参数。
9. 本案例中 Druid 打印时尚未建连，而 C3P0 打印时会初始化池并尝试预建连接。
10. 当前 `BookDao.save()` 没有执行 SQL，它只用于验证 Bean 获取和字符串属性注入。
11. `classpath*:*.properties` 适合展示资源通配符，但生产代码应尽量显式指定配置文件。
12. 当容器中有多个 `DataSource` 时，按类型查找或自动注入必须解决候选对象不唯一的问题。

这个案例的核心并不是“如何操作数据库”，而是理解一条更基础的 Spring 配置链路：

```text
Maven 引入第三方类
        ↓
XML 把第三方对象注册为 Bean
        ↓
properties 提供外部配置
        ↓
Spring 解析占位符并调用 setter 注入
        ↓
应用从 IoC 容器获取配置完成的对象
```

掌握这条链路后，再学习 `JdbcTemplate`、声明式事务、MyBatis 或 Spring Boot 自动配置会更容易理解它们在底层替你完成了哪些工作。

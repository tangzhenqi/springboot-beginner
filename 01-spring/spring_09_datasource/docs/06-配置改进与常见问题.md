## 11. 属性占位符的推荐配置方式

案例为了演示通配符，使用了：

```xml
<context:property-placeholder location="classpath*:*.properties"/>
```

真实项目更推荐缩小加载范围：

```xml
<context:property-placeholder
    location="classpath:jdbc.properties,classpath:jdbc2.properties"
    system-properties-mode="NEVER"/>
```

或将配置放入专用目录：

```xml
<context:property-placeholder
    location="classpath:config/database.properties"
    system-properties-mode="NEVER"/>
```

推荐让配置键带有明确前缀：

```properties
demo.datasource.driver=com.mysql.jdbc.Driver
demo.datasource.url=jdbc:mysql://127.0.0.1:3306/spring_db
demo.datasource.username=root
demo.datasource.password=root
demo.book.name=root666
```

这样比 `username` 之类的通用键更不容易与系统属性、依赖 JAR 或其他模块中的属性重名。

## 12. 案例中值得注意的问题

### 12.1 明文密码

`jdbc.properties` 和 XML 都保存了明文数据库密码。这在教学环境中直观，但生产环境不应把真实凭据提交到 Git。可以通过环境变量、外部配置文件、密钥管理服务或部署平台的 Secret 机制提供敏感信息。

### 12.2 通配符范围过大

`classpath*:*.properties` 可能加载依赖 JAR 中的同类资源。如果出现同名键，最终结果会受到资源集合及覆盖顺序影响，排查困难。显式列出配置文件更稳妥。

### 12.3 容器中存在多个 `DataSource`

当前共有三个数据源 Bean。按名称查询没有问题，但按 `DataSource` 类型自动注入时会产生歧义。真实项目一般只保留一个主数据源，或为多个数据源建立清晰的命名、限定符和路由策略。

### 12.4 无名 Bean 不便使用

来自 properties 的 Druid Bean 没有 `id`，只能依赖自动生成的名称或按类型查找。建议写成：

```xml
<bean id="dataSourceFromProperties"
      class="com.alibaba.druid.pool.DruidDataSource">
    ...
</bean>
```

### 12.5 连接池配置不应照搬

`maxPoolSize=1000` 只是教学示例。连接池大小必须结合：

- 数据库 `max_connections`；
- 应用实例数量；
- 单次 SQL 执行时间；
- 并发请求量；
- 数据库 CPU、内存和 I/O 能力。

连接数过大不仅不会线性提高吞吐量，还可能加剧锁竞争、上下文切换和数据库资源耗尽。

### 12.6 依赖版本较旧

案例使用 Spring 5.2.10、Druid 1.1.16、C3P0 0.9.1.2 和 MySQL Connector/J 5.1.47，适合理解传统 XML 配置，但不宜不经评估直接作为新生产项目的版本组合。升级依赖时需要同步检查：

- Java 版本要求；
- MySQL 驱动坐标与驱动类名；
- `javax.*` / `jakarta.*` 迁移影响；
- 连接池配置项是否变化；
- 已知漏洞和兼容性说明。

### 12.7 应显式关闭上下文

连接池持有连接和后台线程。示例程序最好让 Spring 上下文在结束时执行销毁逻辑，例如：

```java
try (ClassPathXmlApplicationContext ctx =
         new ClassPathXmlApplicationContext("applicationContext.xml")) {
    // 获取并使用 Bean
}
```

对于第三方池，也可以在 XML 中依据其 API 显式声明合适的 `destroy-method`。这样应用停止时能释放连接池资源，避免测试程序残留后台线程。
